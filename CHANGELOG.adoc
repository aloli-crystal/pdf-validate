== v0.30.0 — 2026-06-04 — XMP predefined / extension schemas (§ 6.6.2.3.1)

=== Added

* **`xmp_property_schemas_valid` (§ 6.6.2.3.1)** — every XMP property
  actually used must belong to a predefined schema (the XMP 2005
  schemas plus the standardised PDF/A, PDF/UA and PDF/X identification
  schemas) or to a PDF/A extension schema declared in the packet. The
  RDF parser collects the namespace of each property (element children
  and non-RDF/XML attributes of every `rdf:Description`) and compares
  it to `PREDEFINED_XMP_NAMESPACES` plus the declared
  `pdfaSchema:namespaceURI` values. An unused `xmlns` declaration is
  ignored — only properties count. Leaves `not_covered_tests`.
* `XmpExtensionSchema` now exposes `declared_namespaces` and
  `used_property_namespaces` ; `Context#xmp_property_schema_violations`.
* Specs : a property in an undeclared custom namespace (detected) ; the
  same property declared via an extension schema (clean) ; predefined
  dc/xmp/pdf/pdfaid properties (clean).

== v0.29.0 — 2026-06-04 — Content stream Resources association (§ 6.2.2 t2)

=== Added

* **`content_resources_associated` (§ 6.2.2 t2)** — a content stream
  that references named resources (a font via `Tf`, an XObject via
  `Do`, an ExtGState via `gs`, a shading via `sh`) must have its own
  /Resources dictionary rather than inheriting one from an ancestor
  /Pages node. The `ContentStreamScanner` flags resource usage
  (`uses_named_resources?`) ; the `Context` flags a page that uses
  resources, lacks its own /Resources and has an ancestor that supplies
  one. Leaves `not_covered_tests`.
* `Context` accessor : `resource_inheritance_violations`, with the
  private helper `inherited_resources?`.
* Specs : a page using /F1 Tf with Resources only on the parent /Pages
  (detected) ; the same page with its own /Resources (clean).

== v0.28.0 — 2026-06-04 — Cross-reference table EOL (§ 6.1.4 t2)

=== Added

* **`xref_eol_valid` (§ 6.1.4 t2)** — a single EOL marker separates the
  `xref` keyword and its cross-reference subsection header. Checked on
  the raw bytes ; only classic cross-reference tables are affected
  (files using cross-reference streams have no `xref` keyword), and
  `startxref` is excluded (its `xref` is not line-initial). A candidate
  must be a line-initial `xref` followed by EOL marker(s) then a digit,
  so binary data is never mistaken for a table.
* `Context` accessor : `xref_eol_violations`, with the private helpers
  `count_eol_markers` and `digit?`.
* Specs : a doubled EOL after `xref` (detected) ; a single EOL (clean).

== v0.27.0 — 2026-06-04 — Inline image filter (§ 6.1.10)

=== Added

* **`inline_image_filters_valid` (§ 6.1.10)** — the `ContentStreamScanner`
  now tracks the BI…ID state of an inline image and inspects the value
  of its /F (or /Filter) key — a single name or an array — flagging the
  LZW filter (/LZW or /LZWDecode) and /Crypt.
* `Context` accessor : `inline_image_filter_violations` (aggregated over
  all page content streams via `content_scan`).
* Specs : an inline image with /F /LZW (detected) ; LZW inside a /Filter
  array (detected) ; an inline image with /Fl (clean) ; a document with
  no inline images (clean).

=== Deferred

* **§ 6.1.8 t1** (font / colourant / structure-type names must be valid
  UTF-8 after `#XX` expansion) is *not* implemented and *not* counted :
  the `pdf` parser decodes each `#XX` escape into a Unicode codepoint
  and re-encodes it as UTF-8, so a name is always valid UTF-8 at the
  object-model level — the original byte sequence is lost. Detecting a
  non-UTF-8 name would require the reader to preserve raw name bytes or
  a byte-level correlation of name positions to their semantic roles.

== v0.23.0 — 2026-06-04 — Page transparency groups (§ 6.2.10 t2) & optional-content /Order (§ 6.9 t3)

=== Added

* **`page_transparency_groups_valid` (§ 6.2.10 t2)** — a page that
  contains transparency must carry a /Group whose value is a
  transparency attribute dictionary with a /CS blending colour space,
  unless the document declares a PDF/A OutputIntent (veraPDF
  short-circuits the test to a pass when the output intent colour space
  is known, and so do we). Transparency is detected conservatively : an
  explicit /Group /S /Transparency, or an ExtGState in the page's
  resources that uses a soft mask, a non-standard blend mode, or a
  constant alpha below 1.

  optional-content configuration carries an /Order key, that array must
  reference every OCG in the file (nested group arrays with an optional
  leading label string are flattened). This test leaves
  `not_covered_tests`, so § 6.9 reaches 4/4.
* `Context` accessor : `page_transparency_group_violations`, with
  private helpers `page_contains_transparency?`,
  `extgstate_uses_transparency?` and `collect_order_ocgs`.
* Specs : a transparency page with no /Group /CS (detected) ; the same
  page with a /Group /CS (clean) ; an /Order omitting an OCG (detected)

== v0.19.0 — 2026-06-03 — XMP/RDF parser: PDF/A extension schema (§ 6.6.2.3)

=== Added

* **`XmpExtensionSchema` — an RDF parser for the PDF/A extension
  schema** in the XMP (via `XML.parse`/libxml). It validates the
  structure § 6.6.2.3 requires :
** the `pdfaExtension:schemas` container is an `rdf:Bag` (t1) ;
** `pdfaSchema` : `schema`/`namespaceURI`/`prefix` required (t2-t4),
   `property`/`valueType` lists ;
** `pdfaProperty` : `name`/`valueType`/`description` required,
   `category` ∈ {internal, external} (t7-t10) ;
** `pdfaType` : `type`/`namespaceURI`/`prefix`/`description` + `field`
   (t11-t15) ;
** `pdfaField` : `name`/`valueType`/`description` (t16-t18) ;
** no undefined field in a resource (§ 6.6.2.3.2).
+
The parser navigates by **namespace URI** (not by textual prefix), so
locating a field also proves it sits in the right namespace. Both RDF
serialisations (child element or attribute) are handled.
* `Context` accessor : `xmp_extension_schema_violations`.
* Parser unit specs (valid schema accepted, missing prefix → t4,
  invalid category → t9, undefined field → § 6.6.2.3.2) + integration.

=== Calibrated against veraPDF

Developed with veraPDF 1.30.1 as the oracle : a forged *valid*
extension schema passes all 21 § 6.6.2.3 rules in veraPDF **and**
yields no violation here ; the invalid variants fail at exactly the
same tests (t4 prefix, t9 category).

=== Fixed — false positive on third-party PDF/A

* **`xmp_property_present` / `xmp_property_equals` match both RDF
  serialisations.** The 0.3.0 pdfaid rules used a literal
  `xmp_contains("<pdfaid:part>")`, which only matched the *element*
  form. Ghostscript / ocrmypdf write the equally-valid *attribute*
  form `pdfaid:part="2"`, so `pdf-validate` wrongly rejected genuine
  third-party PDF/A files that veraPDF accepts. The pdfaid (and
  pdfuaid) rules now use the serialization-robust primitives.

  1.30.1, unchanged.

  `ocrmypdf --output-type pdfa` (an independent writer). Before the
  fix : 0/4 (all wrongly rejected). After : **4/4** agreement with
  veraPDF. A Ghostscript fixture is committed as a regression guard.

This is exactly the loop the RATIONALE describes : a diverse,
third-party corpus surfaced a real false positive that a
self-generated corpus could never reveal. The honest takeaway —
generated-corpus agreement (100 %) measures the engine ; third-party
agreement measures *coverage*, and that is where the remaining work
lives (per-resource colour, transparency, annotations…).
