== v0.14.0 — 2026-06-03 — Content-stream interpreter, milestone 1 (§ 6.2.2 / § 6.1.13 t8)

=== Added

* **`ContentStreamScanner` — the content-stream interpreter
  foundation.** It tokenises, in a single pass, the *decoded* bytes of
  a content stream, skipping operands (numbers, strings, names, arrays,
  dictionaries) and **inline-image data** (between `ID` and `EI`) to
  isolate the operators.
** `content_operators_defined` (§ 6.2.2 t1) — every operator in a page
   content stream must be defined in ISO 32000-1 (the operand keywords
   `true`/`false`/`null` are recognised as such).
** § 6.1.13 t8 — the `q`/`Q` graphics-state stack is nested at most 28
   levels deep ; this test leaves `not_covered_tests`.
* `Context` accessors : `undefined_content_operators` and the
  aggregated `content_scan` (operators + max q/Q depth across all
  pages), with the `page_content_bytes` helper (single stream or array
  of streams concatenated).
* Direct `ContentStreamScanner` unit specs (defined operators, unknown
  operator, boolean keywords, q/Q depth, no tokenising inside strings,
  inline-image skip) + integration.

Next interpreter milestones (same bytes, plus graphics state) :

== v0.13.0 — 2026-06-03 — Hardened XMP (§ 6.6.2.1 / § 6.6.4)

=== Added

* **`xmp_well_formed` (§ 6.6.2.1)** — the XMP packet header
  (`<?xpacket …?>`) shall not carry a `bytes` (t2) or `encoding` (t3)
  attribute, and the packet shall be well-formed XML (t4, via
  `XML.parse` + libxml error inspection).
* **`pdfaid_conformance_valid` (§ 6.6.4 t3)** — when present,
  `pdfaid:conformance` shall be A, B or U (both element and attribute
  RDF forms recognised).
* `Context` accessors : `xmp_metadata_violations`,
  `pdfaid_conformance_violations`.
* Specs : an XMP packet with a forbidden `bytes` attribute + an invalid
  « Z » conformance, and a clean-XMP regression guard.

=== Substance, not metric

The coverage percentage is **unchanged** (49 %) : § 6.6.2.1 and § 6.6.4
were already counted at clause level. The validator previously only
attested the *presence* of the metadata stream and pdfaid ; it now
checks their *validity*. This batch narrows the "optimistic
clause-level vs real" gap — substance, not score. (Still open in § 6.6 :
XMP ↔ /Info consistency, explicit UTF-8, pdfaid prefixes, and the PDF/A
extension schema § 6.6.2.3.)

=== Cross-validation (unchanged)

* Generated corpus (60) : **60/60** agreement with veraPDF 1.30.1 — no
  false positives (our XMP has no `bytes`/`encoding`, is well-formed,
  conformance « B »).
* Ghostscript third-party fixture : stays conformant.

== v0.12.0 — 2026-06-03 — Implementation limits (§ 6.1.13)

=== Added

* **`implementation_limits_respected` (§ 6.1.13)** — checks, through
  the object graph, the dictionary subset of the PDF/A-2
  implementation limits :
** integers within ±2³¹ (t1) ;
** reals within ±3.403×10³⁸ (t2) and never closer to zero than
   ±1.175×10⁻³⁸ (t5) ;
** strings ≤ 32767 bytes (t3), names ≤ 127 bytes (t4) ;
** ≤ 8388607 indirect objects (t7) ;
** DeviceN colour spaces ≤ 32 colorants (t9) ;
** page boxes (MediaBox, CropBox, BleedBox, TrimBox, ArtBox) between
   3 and 14400 units (t11).
* `Context` accessor `implementation_limit_violations` (+ the
  `box_dimensions` helper).
* Specs : detection of a degenerate (1×1) MediaBox and a clean-document
  regression guard.

=== Counting honesty — test granularity

* `§ 6.1.13` bundles **ten unrelated limits**. Rather than claim the
  whole clause for the eight tests covered, `doc/gap-analysis/run.sh`
  now counts **at test granularity** (new `not_covered_tests` set) and
  explicitly excludes the two unimplemented tests : t8 (q/Q nesting,
  content-stream interpreter) and t10 (maximum CID value, CMap
  interpreter).

== v0.11.0 — 2026-06-03 — Lexical tokeniser (§ 6.1.6 / § 6.1.7.1 t2 / § 6.1.9)

=== Added

* **`ByteScanner` — a single-pass lexical tokeniser over the raw
  bytes.** It skips the regions that must not be tokenised —
  comments, literal strings and **binary stream data** — so it only
  ever sees genuine PDF syntax. It powers three § 6.1 rules the object
  graph cannot express :
** `hex_strings_valid` (§ 6.1.6) — hexadecimal strings `<…>` have an
   even count of digits, all hexadecimal (correctly distinguishing
   `<<` dictionary open).
** `stream_keyword_eol_valid` (§ 6.1.7.1, t2) — the `stream` keyword
   is followed by CRLF or LF (not a lone CR) and `endstream` is
   preceded by an EOL.
** `indirect_object_spacing_valid` (§ 6.1.9) — an indirect object or
   reference (`N G obj` / `N G R`) separates its parts by a single
   white-space character.
* `Context` accessors : `hex_string_violations`,
  `stream_eol_violations`, `indirect_spacing_violations` (built on a
  memoised `byte_scan`).
* Direct `ByteScanner` unit specs (detection + non-detection +
  not tokenising inside literal strings) and one integration spec
  (odd-length hex string in a page dictionary).

=== Coverage (regenerated via `doc/gap-analysis/run.sh`)

§ 6.1 File structure rises to **12/27 (44 %)**. Total clause-level
coverage : **60/144 (41 %) → 63/144 (43 %)**.

§ 6.1.7.1 test t1 (declared /Length must equal the real stream data
length) is **deferred** : /Length is often an indirect reference and
the EOL before `endstream` is ambiguous, so the false-positive risk is
unacceptable for now.

== v0.10.0 — 2026-06-03 — Raw-byte scanner (§ 6.1.2 / § 6.1.3 t3)

=== Added

* **The validator's first access to the raw file bytes.** The
  `Context` now receives the bytes (via `PDF::Validate.bytes` /
  `.file`), unlocking low-level syntax rules the object graph cannot
  see.
** `file_header_valid` (§ 6.1.2) — the file must begin at byte 0 with
   `%PDF-1.n` (n in 0..7) followed by an EOL (t1), and the next line
   must be a `%` comment followed by at least four bytes > 127 — the
   binary marker (t2).
** `no_data_after_eof` (§ 6.1.3, t3) — nothing shall follow the final
   `%%EOF` except a single optional EOL.
* New `Context` accessors : `file_header_violations`,
  `data_after_eof_violations` (and the `last_eof_offset` helper). When
  the raw bytes are unavailable (validating an already-open reader),
  these rules report nothing rather than guess.
* Positive-detection specs : a file with no binary marker, and a file
  with bytes after the final `%%EOF`. The test PDF builder now emits
  the binary marker by default.

== v0.8.0 — 2026-06-03 — § 6.3 Annotations (complete section)

=== Added

== v0.7.0 — 2026-06-03 — § 6.2 batch 2 (images, ICC profile, rendering intent)

=== Added

* **Three more § 6.2 Graphics clauses**, all dictionary-checkable :
** `image_dictionary_keys_valid` (§ 6.2.8) — an image XObject
   dictionary shall not contain /Alternates (t1) or /OPI (t2),
   /Interpolate shall be false if present (t3), /BitsPerComponent
   shall be 1/2/4/8/16 (t4) — or 1 for an image mask (t5).
** `output_intent_profiles_valid` (§ 6.2.3) — the DestOutputProfile
   ICC profile shall be a "prtr"/"mntr" class profile in RGB/CMYK/GRAY
   colour space, ICC version < 5 (t1, read from the decoded ICC
   header) ; multiple OutputIntents shall share one indirect profile
   (t2) ; a PDF/X output intent shall not carry /DestOutputProfileRef
   (t3).
** `rendering_intents_valid` (§ 6.2.6) — an image /Intent shall be one
   of the four ISO 32000-1 values (the content-stream `ri` operator
   form is not reached by a dictionary walk — documented partial
   coverage).
* New `Context` accessors : `image_dictionary_violations`,
  `output_intent_profile_violations`, `invalid_rendering_intents`.
* The validator reads the ICC header from the stream's **decoded**
  bytes (the reader inverts FlateDecode on parse) : device class at
  offset 12, colour space at offset 16, major version at offset 8.
* Positive-detection specs (hand-authored PDFs) : an image with
  non-conformant keys + an invalid rendering intent ; a "spac"-class
  DestOutputProfile. The test PDF builder now supports stream objects.

=== Changed

* `pdf` dependency bumped to **`~> 1.0`** (from `~> 0.7.5`). The
  § 6.2.3 rule revealed that the bundled `lib/pdf` (0.7.5) still
  produced an sRGB v4 "spac"-class output intent — which veraPDF
  rejects. `pdf` 1.0.0 uses the correct sRGB2014 "mntr" display
  profile. In other words : **the new rule immediately caught a real
  conformance defect in our own dependency.**

== v0.5.0 — 2026-06-02 — ISO 19005-2 gap analysis + clause reconciliation

=== Added

* **`doc/iso-19005-2-gap-analysis.adoc`** — an état des lieux of
  `pdf-validate` versus the full ISO 19005-2 rule set, using
  veraPDF 1.30.1's open validation profile as the authoritative
  (machine-readable) encoding of the standard. Clause-level coverage
  by section, an honest reading of the number, and a prioritised
  backlog of what is missing.
* **`doc/gap-analysis/run.sh`** — regenerates the coverage table from
  a veraPDF run, so the analysis is reproducible.

=== Headline

Clause-level coverage : **26 / 144 ≈ 18 %** of the rules veraPDF
applies for PDF/A-2b. Per section : Actions 100 %, Metadata 36 %,
Graphics 13 %, File structure 11 %, and 0 % for Annotations,
Signatures, Embedded files, Optional content, Alternate
presentations, Requirements. The 60/60 and 4/4 agreement scores hold
*within* this covered subset ; the gap is where third-party PDFs
exercising uncovered clauses could slip through.

=== Fixed — clause references reconciled with the standard

* The hand-assigned ISO clause numbers in `rules/pdf-a-2b.yml` were
  wrong in several places (pdfaid was tagged § 6.7.11 — which does
  not exist ; fonts § 6.3.4 ; JavaScript/AA § 6.6). Reconciled with
  the real ISO 19005-2 structure as encoded by veraPDF :
  pdfaid → § 6.6.4, metadata → § 6.6.2.1, fonts → § 6.2.11.4.1,
  output intent → § 6.2.10, image colour → § 6.2.4.3, JavaScript
  → § 6.5.1, /AA → § 6.5.2. Rule ids updated accordingly. This makes
  every `pdf-validate` report cite the correct ISO clause — the whole
  point of an audit trail.

== v0.4.0 — 2026-06-02 — More rules ; serialization-robust XMP ; third-party corpus

=== Added

* **More PDF/A-2b rules** :
** `no_javascript` (§ 6.6.1) — fails if any JavaScript action is
   reachable (a dict with `/S /JavaScript`, or `/Names /JavaScript`).
** `/AA` forbidden in the catalog (§ 6.6.2).
** `image_colorspaces_calibrated` (§ 6.2.4) — flags image XObjects in
   bare DeviceRGB/DeviceCMYK when the document has no OutputIntent.
* New check primitives : `no_javascript`, `image_colorspaces_calibrated`,
  and the serialization-robust `xmp_property_present` /
  `xmp_property_equals`.
* `Context#each_object` — the shared object-graph walker the
  graph-scanning checks build on.

=== Fixed — false positive on third-party PDF/A

* **`xmp_property_present` / `xmp_property_equals` match both RDF
  serialisations.** The 0.3.0 pdfaid rules used a literal
  `xmp_contains("<pdfaid:part>")`, which only matched the *element*
  form. Ghostscript / ocrmypdf write the equally-valid *attribute*
  form `pdfaid:part="2"`, so `pdf-validate` wrongly rejected genuine
  third-party PDF/A files that veraPDF accepts. The pdfaid (and
  pdfuaid) rules now use the serialization-robust primitives.

=== Cross-validation — now including third-party documents

* Generated corpus (pdf-a output) : **60/60** agreement with veraPDF
  1.30.1, unchanged.
* **Third-party corpus** : PDF/A-2b files produced by Ghostscript via
  `ocrmypdf --output-type pdfa` (an independent writer). Before the
  fix : 0/4 (all wrongly rejected). After : **4/4** agreement with
  veraPDF. A Ghostscript fixture is committed as a regression guard.

This is exactly the loop the RATIONALE describes : a diverse,
third-party corpus surfaced a real false positive that a
self-generated corpus could never reveal. The honest takeaway —
generated-corpus agreement (100 %) measures the engine ; third-party
agreement measures *coverage*, and that is where the remaining work
lives (per-resource colour, transparency, annotations…).

== v0.3.0 — 2026-06-02 — Font-embedding & /ID rules ; 60/60 vs veraPDF

=== Added

* **`all_fonts_embedded` check** — walks the object graph from the
  catalog (resolving references ; `reader.objects` is a lazy cache
  and cannot be relied on) and yields every `/Type /Font` dict. Flags
  simple fonts with no FontDescriptor (the standard-14) and any
  descriptor lacking FontFile/FontFile2/FontFile3. New `pdf-a-2b`
  rule `pdfa2-6.3.4-fonts-embedded`.
* **`/ID` trailer rule** (`pdfa2-6.1.3-file-id`) — PDF/A requires a
  file identifier in the trailer.

=== Cross-validation against veraPDF 1.30.1

On a 60-PDF corpus generated by `pdf-a` (36 conformant PDF/A-2b +
24 each violating one requirement: non-embedded font, no output
intent, no pdfaid, no /ID, encryption), `pdf-validate` and **veraPDF
1.30.1 agree on 60/60 verdicts (100 %)** — exceeding the J5 exit
criterion (≥ 95 % on 60 PDFs).

CAVEAT, stated plainly : this corpus is *generated by the ALOLI
shards* (homogeneous provenance), and `pdf-validate` implements ~8
document- and font-level rules versus veraPDF's 144. 100 % agreement
here demonstrates the engine matches veraPDF **for documents within
the implemented rule set's scope** — it is NOT a claim of veraPDF
parity on arbitrary third-party PDFs across every ISO 19005-2 clause.
Reaching that needs the per-resource rules (colour spaces,
transparency, annotations…) layered in over time, ideally
cross-checked against a diverse third-party corpus.

== v0.1.0 — 2026-06-02 — Declarative engine + pdf-a-2b (J5, palier 1)

=== Added

* Generic declarative validation engine : `Rule` (YAML), `Context`
  (parses the PDF via `PDF::Reader`, exposes catalog/trailer/XMP),
  `Checks` (vocabulary of primitives), `Engine`, `Report` (text +
  JSON).
* `RuleSet` — YAML rule sets baked into the binary at compile time,
  so the validator is self-contained.
* `rules/pdf-a-2b.yml` — 6 document-level PDF/A-2b rules.
* CLI `bin/pdf-validate` : `-p/--profile`, `-j/--json`, `-q/--quiet`,
  positional `help`, `-h/--help`, `-v/--version` ; exit 0/1/2.
* Top-level entry points `PDF::Validate.file` / `.bytes` / `.run`.
