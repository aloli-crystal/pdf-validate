== v0.4.0 — 2026-06-02 — Plus de règles ; XMP robuste ; corpus tiers

=== Ajouté

* **Nouvelles règles PDF/A-2b** :
** `no_javascript` (§ 6.6.1) — échoue si une action JavaScript est
   atteignable (dict avec `/S /JavaScript`, ou `/Names /JavaScript`).
** `/AA` interdit dans le catalog (§ 6.6.2).
** `image_colorspaces_calibrated` (§ 6.2.4) — signale les images
   XObject en DeviceRGB/DeviceCMYK nu quand le document n'a pas
   d'OutputIntent.
* Nouvelles primitives : `no_javascript`, `image_colorspaces_calibrated`,
  et les robustes `xmp_property_present` / `xmp_property_equals`.
* `Context#each_object` — le walker du graphe d'objets partagé par
  les checks qui scannent le graphe.

=== Corrigé — faux positif sur PDF/A tiers

* **`xmp_property_present` / `xmp_property_equals` reconnaissent les
  deux sérialisations RDF.** Les règles pdfaid de 0.3.0 utilisaient
  un `xmp_contains("<pdfaid:part>")` littéral, qui ne matchait que la
  forme *élément*. Ghostscript / ocrmypdf écrivent la forme
  *attribut* — tout aussi valide — `pdfaid:part="2"`, si bien que
  `pdf-validate` rejetait à tort de vrais PDF/A tiers que veraPDF
  accepte. Les règles pdfaid (et pdfuaid) utilisent désormais les
  primitives robustes.

=== Validation croisée — incluant désormais des documents tiers

* Corpus généré (sortie pdf-a) : **60/60** d'accord avec veraPDF
  1.30.1, inchangé.
* **Corpus tiers** : PDF/A-2b produits par Ghostscript via
  `ocrmypdf --output-type pdfa` (un écrivain indépendant). Avant le
  fix : 0/4 (tous rejetés à tort). Après : **4/4** d'accord avec
  veraPDF. Une fixture Ghostscript est committée en garde de
  non-régression.

C'est exactement la boucle décrite par le RATIONALE : un corpus tiers
diversifié a révélé un vrai faux positif qu'un corpus auto-généré ne
pouvait pas montrer. Le constat honnête — l'accord sur corpus généré
(100 %) mesure le moteur ; l'accord tiers mesure la *couverture*, et
c'est là que vit le travail restant (couleur par ressource,
transparence, annotations…).

== v0.3.0 — 2026-06-02 — Règles polices & /ID ; 60/60 vs veraPDF

=== Ajouté

* **Check `all_fonts_embedded`** — parcourt le graphe d'objets depuis
  le catalog (en résolvant les références ; `reader.objects` est un
  cache paresseux non fiable) et visite chaque dict `/Type /Font`.
  Signale les polices simples sans FontDescriptor (les standard-14)
  et tout descripteur sans FontFile/FontFile2/FontFile3. Nouvelle
  règle `pdf-a-2b` `pdfa2-6.3.4-fonts-embedded`.
* **Règle `/ID` du trailer** (`pdfa2-6.1.3-file-id`) — PDF/A exige un
  identifiant de fichier dans le trailer.

=== Validation croisée contre veraPDF 1.30.1

Sur un corpus de 60 PDF généré par `pdf-a` (36 conformes PDF/A-2b +
24 violant chacun une exigence : police non embarquée, pas d'output
intent, pas de pdfaid, pas de /ID, chiffrement), `pdf-validate` et
**veraPDF 1.30.1 sont d'accord sur 60/60 verdicts (100 %)** —
dépassant le critère de sortie J5 (≥ 95 % sur 60 PDF).

RÉSERVE, dite clairement : ce corpus est *généré par les shards
ALOLI* (provenance homogène), et `pdf-validate` implémente ~8 règles
de niveau document/police contre les 144 de veraPDF. Les 100 %
d'accord ici démontrent que le moteur est en phase avec veraPDF
**pour les documents dans le périmètre des règles implémentées** — ce
n'est PAS une revendication de parité veraPDF sur des PDF tiers
arbitraires sur toutes les clauses ISO 19005-2. L'atteindre demande
les règles par ressource (espaces de couleur, transparence,
annotations…) ajoutées au fil du temps, idéalement croisées avec un
corpus tiers diversifié.

== v0.2.0 — 2026-06-02 — Profil PDF/UA-1

=== Ajouté

* **Profil `pdf-ua-1`** — nouveau jeu de règles
  (`rules/pdf-ua-1.yml`) couvrant les exigences PDF/UA-1
  (ISO 14289-1) de niveau document : identification pdfuaid, arbre
  de structure logique (`/StructTreeRoot`), `/MarkInfo`, langue du
  document (`/Lang`), `/ViewerPreferences`, métadonnées XMP. Le
  validateur couvre désormais PDF/A *et* PDF/UA.
+
[source,console]
----
$ pdf-validate accessible.pdf -p pdf-ua-1
----

=== Modifié

* Contrainte passée à `pdf ~> 0.7.5` (hooks PDF/UA).

== v0.1.0 — 2026-06-02 — Moteur déclaratif + pdf-a-2b (J5, palier 1)

=== Ajouté

* Moteur de validation déclaratif générique : `Rule` (YAML),
  `Context` (parse le PDF via `PDF::Reader`, expose
  catalog/trailer/XMP), `Checks` (vocabulaire de primitives),
  `Engine`, `Report` (texte + JSON).
* `RuleSet` — jeux de règles YAML embarqués dans le binaire au
  compile-time, validateur self-contained.
* `rules/pdf-a-2b.yml` — 6 règles PDF/A-2b de niveau document.
* CLI `bin/pdf-validate` : `-p/--profile`, `-j/--json`,
  `-q/--quiet`, `help` positionnel, `-h/--help`, `-v/--version` ;
  exit 0/1/2.
* Points d'entrée `PDF::Validate.file` / `.bytes` / `.run`.
